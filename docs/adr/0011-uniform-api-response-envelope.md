# Uniform API response envelope

Every `/api/v1` response carries a wrapper. Successes are `{ data }`, with a sibling `meta` only where a collection paginates. Failures are `{ error: { code, message, details? } }`, where `code` is a stable string from a closed set and is the only thing the frontend branches on. A global error handler and not-found handler reshape Fastify's own errors into the same envelope, so malformed bodies, unsupported media types and unmatched routes cannot return a third shape.

The envelope is chosen over bare resource bodies because of what the API is committed to becoming, not because of what it serves today. A bare top-level array cannot gain pagination metadata without either breaking its clients or moving that metadata into headers, and administrative collections are already committed to carrying it. Wrapping uniformly costs one unwrap in the client's HTTP layer and buys the ability to add response metadata to any endpoint without a version break. Wrapping only collections was rejected outright: an API where the shape depends on the endpoint pushes that knowledge to every call site.

Splitting `code` from `message` keeps the product's voice on the frontend. If the backend supplied display copy, it would own the wording of every visitor-facing error and foreclose translation. Instead `message` is developer-facing, the frontend maps `code` to what a person reads, and a new code is minted only when the frontend must render something different — a rule that keeps the set small enough to stay closed without a registry. Optional field errors in `details` use react-hook-form's dotted path notation, so one adapter maps any error onto any form, including conflicts and domain-rule rejections rather than validation failures alone. RFC 9457 problem details was considered and rejected as disproportionate for a single-owner portfolio.

Request validation and response serialization both run from Zod schemas declared on the route, rather than from Fastify's native JSON Schema or from `safeParse` calls inside handlers. Zod already describes the contract on the web side, so this keeps one schema language across both applications and leaves route schemas declarative enough to generate OpenAPI from later. Validating inside handlers was rejected because Fastify's own validation failures would then produce a different body from the handler's, which is the exact inconsistency this decision exists to prevent. The accepted cost is that a response schema narrower than reality drops fields silently, which makes response shape a thing tests must assert at the HTTP boundary.

The Better Auth subtree is a deliberate exception. It emits its own error shape and could only be brought into the envelope by wrapping each of its routes. Because the web application talks to it through the Better Auth client rather than the shared HTTP instance, its responses never reach the code path that assumes this envelope.
