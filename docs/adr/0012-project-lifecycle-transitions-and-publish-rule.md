# Project lifecycle transitions and the minimum publish rule

A Project's lifecycle state changes through four dedicated endpoints — `publish`, `unpublish`, `archive`, `unarchive` — rather than a generic `PATCH` carrying a new `state`. The legal graph is Draft → Published, Published → Draft, Published → Archived, and Archived → Draft. Archived → Published direct and Draft → Archived are not offered: leaving Archived always passes back through Draft, and reaching Archived always passes through Published.

Dedicated endpoints were chosen because `publish` is not a peer of the other three: it alone carries real business validation, so a single `PATCH` handler would still branch internally on the target state, just without the branch showing up in the API surface. Restricting the graph to two round trips (Draft⇄Published, Published⇄Archived's one-way arm closed by Archived→Draft) keeps every transition symmetric with an undo, without adding a direct Archived→Published shortcut that would let a Project skip re-validation on its way back to Published.

Publishing runs a domain predicate, `canPublish(project)`, checking that `summary` is non-empty, at least one of the five Case study sections is non-empty, and at least one Category is assigned. Technology, the two links, and the professional-context fields (`clientName`, `role`, dates) stay optional even when Published — the schema already allows a Draft to be saved half-written (see [#2](https://github.com/Maykiyel/fullstack-portfolio/issues/2)), and this rule only closes the subset of that gap that would make a live public page embarrassing to look at, not the subset docs/development.md defers to slice 4's "stronger publish validation." The predicate lives in domain/application code, not the Zod schema on the route: Zod validates that a request is well-formed, `canPublish` validates that a specific persisted row is allowed to become public, and the two would look confusingly similar if merged.

Two failure modes are kept distinct. Calling a transition from the wrong current state (`publish` on an already-Published Project, `archive` on a Draft one) is `409 INVALID_STATE_TRANSITION` — a conflict between the request and the resource's current state, not a defect in the resource itself. Failing `canPublish` is `422 PROJECT_NOT_PUBLISHABLE`, with one `details` entry per unmet requirement and no `path` on any of them, per the root-level convention [#7](https://github.com/Maykiyel/fullstack-portfolio/issues/7) already reserved for domain-rule rejections that don't belong to a single form field.

`publishedAt` is overwritten on every transition into Published, not fixed at the first. Nothing in the domain model asks for an immutable "originally published" date, and treating the field as "most recent publish time" is both the simpler rule and the cheaper implementation — no first-time branch. A permanent original-publish record, if ever wanted, is an additive field rather than a reason to complicate this one.

Soft deletion (`deletedAt`) is untouched by this decision. [#2](https://github.com/Maykiyel/fullstack-portfolio/issues/2) already ships the column with no `DELETE` endpoint in slice 1, so no transition here can set it, and its interaction with lifecycle state is deferred along with the endpoint that would trigger it.
